# contract-build · 契约施工法

> **人写契约与回执，AI 写代码，测试当缰绳。**

一套让「AI 大规模生成代码」不塌质量的施工流程，从开源项目 [AI-Resonance](https://github.com/WZZNNE/AI-Resonance) 的实际施工方式反向提炼考证还原而来。这个skill来源很复杂，完全基于个人化的提炼，在提炼施工方法后续又添加了ui设计方面契约，还有部分零散优化方案叠加出来。



### 契约施工法全程围绕契约来完成施工，审查，修复，回执全流程，契约不止包含逻辑功能，也可以配合UIskill来规范UI契约，达到统一UI风格色调的目的。核心契约覆盖的越完整需要人工干预就越少，最终实现无需看管。skill会显著token消耗使用请评估余额是否充足。

# 施工实例：

1.先确定基础功能（参考一般浏览器的功能），提出核心期望（沉浸式使用网页，UI使用可隐藏的悬浮面板），让agent完全围绕核心期望来设计

2.产出htm效果图，关于颜色，大小，位置等微调部分建议让ai作出带调参功能面板的效果页面，手动拖动功能面板来快速微调到满意，再由agent来实现

3.首次施工：使用契约施工工作流（工作流：zcode可调用多子代理同步施工，其他agnet未测试）完成项目，后续修改小功能应该不会调用skill（如果还是调用请在agent添加记忆规范什么时候使用施工法），在多轮修改，大功能实现或者大规模优化重构，主动要求使用契约施工（agent会在合适时机主动调用）。
再次声明，skill目标是许愿式编程远远达不到商业化项目要求，主要用于定制化个人化软件可以很便捷实现，或者功能验证demo

## 它解决什么

AI 写代码的瓶颈不是生成，是**不漂移**。规模一上来质量就塌，这套方法用四道闸防同一件事：

| 闸 | 手段 | 防什么 |
|---|---|---|
| 契约 | 把「长什么样 / 不许什么样」前置成**值级条款** | 需求靠对话口头传，各写各的 |
| 测试 | 把正确性变成**可重跑的运行时校验** | 改 A 崩 B，没人知道 |
| 独立审查 | 用**无污染上下文**兜底 | 施工者看自己的代码有惯性，自我背书 |
| 回执 | 把「验证到什么程度」显式化，**含未验证项** | 没测的东西藏起来，下一波爆雷 |

## 安装

本技能是标准 Agent Skill：`SKILL.md` 放在仓库根目录，任何读 `~/.agents/skills` 的工具（ZCode、Codex 等）都会自动发现，**新会话生效**。

```bash
git clone https://github.com/<你的用户名>/contract-build.git ~/.agents/skills/contract-build
```

已有目录时更新：

```bash
cd ~/.agents/skills/contract-build && git pull
```

不装也能用：把 `SKILL.md` 的内容贴进会话，让模型按流程走。

## 流程总览

```
P0 契约 ──【闸:用户确认】──▶ P1 爆发 ──▶ P2 独立审查 ──▶ P3 修复轮 ──▶ P4 回执 ──【闸:用户验收】
                                                                    │
                                                       (视觉类)P5 减法 ──▶ P6 沉淀(每波结束)
```

| 阶段 | 做什么 | 关键纪律 |
|---|---|---|
| **P0 契约** | 产出 `DESIGN.md` / `VISUAL.md`（工程或视觉契约）、`VERIFIED.md`（证据台账）、验收标准 | 值 = 代码里的值，写死具体值不写形容词；演进只加「取代条款」；**契约未经用户确认，P1 不动工** |
| **P1 爆发** | 按契约一次生成到位，测试与 fixture 随实现同步落地 | 指挥官纪律：定向三问 → 碰撞预防 → 任务书落纸；**只给子代理契约路径与目标，不给施工对话** |
| **P2 独立审查** | **必须新开子代理**（全新上下文），只喂契约 + 代码 | 审查者不得与实施者同上下文；产出编号清单，分「契约违背 / 缺陷 / 未验证项」三栏 |
| **P2' 快速迭代** | 连续小波次可豁免审查，但须记账 | 未审波次累计 ≥5、或触及浮层/状态机/手势/输入法/多模块交叉，即恢复全审 |
| **P3 修复轮** | 按 review 清单逐条修，**只修清单所列** | 修复轮计数 N/3：第 3 轮仍有硬伤就停止硬修，升级用户决策，不带病交付 |
| **P4 回执** | 写 `IMPLEMENTATION-<date>.md`，判决行 PASS / NEEDS WORK | 证据不齐就写 NEEDS WORK；验收标准逐条打勾并附验证方式；**必须列出本轮未验证项** |
| **P5 减法** | 视觉/交互类必做，爆发完成**立即**剪枝一轮，不隔夜 | 剪掉的东西回填成契约的 Do Not 条款 |
| **P6 沉淀** | 契约以 vN 取代式演进；改实现不改契约名 | 每波留带日期回执，`docs/` 目录本身就是项目编年史 |

## 何时用 / 不用

**用**：新项目、整站或整模块重写、设计系统级改造、≥3 文件且值得立契约的功能纵切；以及那些以前靠对话口头传需求、返工多的活儿。

**不用**：单点修 bug、小样式调整（契约是负担）；视觉方向还没定（先做视觉方向探索，定稿再施工）；需求本身没想清楚（先做需求盘问）。

## 四条红线

1. 契约没确认不动工 —— 返工几乎都发生在没有闸门的地方。
2. 审查者不得与实施者同上下文 —— 双会话审计的意义就在「无污染」。
3. 回执必须含「未验证项」—— 藏住没测的东西，下一波一定爆雷。
4. 证据不只记结论 —— 置信度（`✔` 实测 / `?` 仅文档）+ 日期 + 反例；结论会过期，证据可复验。

```
references/nexus-handoff-templates.md      NEXUS 交接协议模板快照：标准交接 / QA 回执
```

`references/templates.md` 里的六份模板与流程阶段一一对应：

| # | 模板 | 阶段 | 用途 |
|---|---|---|---|
| 1 | `DESIGN.md` | P0 | 工程契约：原则 / 接口 / 数据 / 错误降级 / Do Not / 测试纪律 |
| 2 | `VISUAL.md` | P0 | 视觉契约：概念 / 原则 / Token 表 / 版面 / 组件规约 / 可达性 / Do Not |
| 3 | `VERIFIED.md` | P0 | 证据台账：逐外部系统记录实测、失败模式、已废信源 |
| 4 | `review-<date>.md` | P2 | 独立审查产出：契约违背 / 缺陷 / 未验证项 / 契议 |
| 5 | `IMPLEMENTATION-<date>.md` | P4 | 实施回执：判决行 + 验收核验表 + 验证证据 + 诚实边界 |
| 6 | 子代理任务书 | P1 | 派单交接：契约路径 + 验收标准 + 完成证明 |

P0 验收标准 → 任务书复选框 → 子代理完成证明 → P4 回执逐条核验，**同一份清单走全程**，每道环节对同一批条目负责。

## 无头模式

整条 P1→P4 链可做成动态工作流脚本，供无头派单：P0 闸门在派单前人工完成、契约已入仓库，脚本里实施 / 审查 / 修复各为独立子代理，回执落盘后回传。
